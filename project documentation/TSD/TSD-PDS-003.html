2.4 Layering and module boundaries

The application is one Laravel project. Boundaries are enforced by folder and by a small set of architectural tests, not by separate packages or services.

LayerLocationRule
Interfaceapp/Http/Controllers, Requests, Resources, Pages (Inertia props)Depends on domain only. Never touches another module's table directly.
Domainapp/Domain/<Context> — Workflow, Project, Spec, Inspection, Supplier, Approval, Access, ReportingOwns its entities, services, gates. Contexts communicate through service interfaces or events, never by importing another context's model for writing.
Infrastructureapp/Support, app/Jobs, app/Console, app/Services (PDF, XLSX, mail)Implementations the domain declares a need for. Swappable.
Clientresources/js/Components read props; they do not compute status, progress or permission.
Why the workflow engine is a context and not a model. FSD §4 makes one engine serve eight document types. If it lived inside, say, the approval module, the drawing and artwork flows would each re-implement it — which is precisely how the rejected prototype ended up with three menus for one thing. The engine owns approval_documents, approval_steps, chain configuration, transitions and derived status; every other context only declares a chain key and reads results.

3. Data design

3.1 Conventions

RuleDetail
Engine, charsetInnoDB, utf8mb4_0900_ai_ci. Material names and remarks contain non-ASCII and must not be silently mangled.
Primary keysid BIGINT UNSIGNED AUTO_INCREMENT internally. Human codes (code, number) are separate unique columns, never the join key — codes are printed, ids are not (FSD §2.3).
Foreign keysReal constraints, ON DELETE RESTRICT everywhere. Nothing in this system is deleted by cascade; deactivation is the mechanism (FSD-402, G-13).
Timestampscreated_at/updated_at stored UTC. Business dates that a human chooses (effective_date, planned_end) are DATE, not timestamps — a date must not shift by an hour across a DST-free but mis-set clock.
Soft deleteOnly on records with no audit consequence: announcements, attachments. Never on workflow, approval, inspection or master data (OQ-09).
MoneyDECIMAL(14,2), whole rupiah in practice; never float. Currency is single (IDR) and not stored per row.
EnumerationsMySQL ENUM is avoided. Status values are VARCHAR(32) with a check constraint plus a PHP enum class, so adding a state is a migration, not a column rebuild.
Numeric toleranceDECIMAL(12,4) for nominal/min/max; unit is a FK to units, never free text, because the inspection form must compare against it.
BooleanTINYINT(1) named is_* or has_*. No nullable booleans: three states are three explicit values.
NamesTables plural snake_case; columns snake_case; pivot tables a_b alphabetical. Indexes idx_<table>_<cols>, uniques uq_<table>_<cols>, FKs fk_<table>_<col>.
JSONAllowed only for genuinely open payload shapes (form impact rows, evidence metadata). Never for anything queried, filtered, or gated.

3.4 Index strategy

Indexes are justified by a named query in this document, not by intuition. The budget is roughly 6–8 secondary indexes per hot table.

IndexServesWhy this shape
approval_documents (doc_status, approval_status_cached, type)Lists, queue counts, dashboard cardsCovering the two predicates every list applies before paging.
approval_steps (assigned_user_id, decision, acted_at)"Waiting on whom", badge countOpen steps are decision IS NULL; the index leads on the actor so the badge query is an index seek.
approval_steps (approval_document_id, seq)Status derivationUnique; the deriver reads one document's steps in order, always.
stage_records (assignment_id, stage_key) UNIQUEStepper render, progress calcOne read per assignment, ordered by seq via join to definitions.
stage_records (status, planned_end)Overdue reportPartial selectivity: most rows are not overdue.
inspections (assignment_id, level, attempt_no) UNIQUEG-05, G-06The gate asks "does a PASS T1 exist for this assignment"; this index answers it as a seek plus one filter.
quotations (assignment_id, status)G-07, comparison viewComparison reads all quotations for one assignment.
notifications (recipient_id, read_at, created_at)Bell panel, unread countOrdered by recency without a filesort.
audit_entries (target_type, target_id, created_at)Per-record history strip (§2.5)The strip is opened constantly; without this it is a table scan.
supplier-scoped FKs on quotations, invitations, submissionsG-14 isolationEvery supplier query filters by supplier_id first; the index makes isolation cheap rather than merely correct.
Generated columns are used sparingly. suppliers.name_key and supplier_evaluations.overall_score are STORED generated columns because they are unique-checked and reported respectively. approval_status_cached is not generated — it depends on another table's rows, which MySQL does not allow in a generated column. It is written by the deriver inside the same transaction (§4.2).

3.5 Immutability and retention

RuleImplementation
Approved documents are immutablePolicy refuses update when doc_status = CLOSED; a revision inserts a new row with revision_of_id. No trigger needed, and no status column can be flipped back by an API client.
Referenced master data is never deletedFK RESTRICT plus an explicit pre-check that returns MSG-070 with the live referencing count (the count is the same subquery the list column uses, so the number shown and the number blocking are identical).
RetentionNo purge job for business data (OQ-09). Only sessions, expired password_resets, and delivered notification rows older than 180 days are pruned, and pruning notifications never removes an unread one.
AuditApplication writes only. The DB user used by the application is granted INSERT/SELECT on audit_entries, not UPDATE/DELETE — enforced by MySQL grants, not by convention (TSD-370).
SequencesAllocated under SELECT … FOR UPDATE; a rolled-back document still consumes its number (BR-13 wants numbers never reused, not gapless).

4. Workflow engine implementation

4.1 Chain configuration and resolution

Chain templates are data (§3.3.5). At submit time the engine snapshots them into approval_steps rows, resolving each role to a concrete user where possible and leaving assigned_user_id NULL where the role has several holders.

IDBehaviourDetail
TSD-401Snapshot, do not reference.Steps copy role_slug, action, seq, parallel_group from the template at submit. Editing a template later changes only documents submitted afterwards. This is what makes a printed signature block still describe reality five years on.
TSD-402Role-to-person resolution order.(1) explicit delegate on the role for this document type; (2) the single holder of the role; (3) if several holders, the step stays role-assigned and any holder may act, first actor wins; (4) if zero holders, submit is refused with a named configuration fault rather than silently dropping the step.
TSD-403Author exclusion at resolution.Resolution never assigns the author to their own document's step (G-01 enforced before display, not only at action time), so the UI does not invite a failure.
TSD-404Sequential vs parallel.approval_chains.is_sequential decides whether step n+1 becomes visible at all. ARTWORK-CIRC is sequential; FAB approvers share one parallel_group and are all open at once. Both are one query: open steps are those with decision IS NULL and, when sequential, the minimum seq among undecided.
TSD-405Required vs optional steps.is_required allows a future "for information" reviewer without changing the deriver's rule that all required steps must be decided.

4.2 Status derivation

StatusDeriver::derive(ApprovalDocument $doc): string
  steps = doc.steps(order: seq)              // uses uq(approval_document_id, seq)
  if doc.doc_status == DRAFT      -> NONE
  if any required step.decision == REJECT -> REJECTED
  if doc.doc_status == CANCELLED  -> REJECTED
  open = steps where decision IS NULL and is_required
  if none open                    -> APPROVED
  if any open with action CHECK   -> CHECKING  (or PENDING_CHECKING before first action)
  if no CHECK steps remain open   -> WAITING_APPROVAL
IDBehaviourDetail
TSD-410Derived on write, cached for lists.Every step decision write calls the deriver inside the same transaction and stores the result in approval_status_cached. Reads for a single document recompute; reads for a list use the cache. Recomputation is cheap (one indexed read of ≤5 rows).
TSD-411Cache integrity check.A nightly job recomputes all non-closed documents and logs any mismatch. It fixes nothing by default; the mismatch is the finding, because a mismatch means a code path wrote a step without going through the deriver.
TSD-412No client-supplied status.Requests may carry an action (approve, reject, return) and never a status. Status is exclusively the deriver's output.

Effects registry. Closing a document must do more than change a status: it opens a stage, records an actual date, and notifies. Rather than scattering if type == 'fab' branches, each document type registers an OnApproved and OnRejected effect class resolved from config/workflow.php. Adding a document type means adding a chain row, a payload table, and one effect class — nothing else. A test asserts every registered type has an effect class, so a new type cannot be added that approves into silence.

5. Authorisation implementation

5.1 Model

IDBehaviourDetail
TSD-501Two layers, one truth.Spatie roles carry the user's role set. The feature_grants table carries the matrix. A permission is synchronised into Spatie only as a cache of the matrix, so the matrix remains the single editable source (FSD-614).
TSD-502Ability naming.<feature>.<level> — e.g. quotation.compare.FULL, specification.view.READ. A FULL grant implies READ; the synchroniser writes both so a can('...READ') check never fails for someone with FULL.
TSD-503Deny by default.No grant row means no permission. There is no "everyone can" row and no fallback allow in the middleware.
TSD-504Menus are data.The navigation tree is filtered server-side by the same grant set the policies use, so a menu item cannot exist for a user who would get MSG-010 clicking it.

5.2 Caching and invalidation

IDBehaviourDetail
TSD-510Per-user permission set cached in the session plus a global cache key.Key perm:user:{id}. The matrix write bumps a global matrix_version; every request compares it and reloads on mismatch. A change takes effect on the next request of every affected user, satisfying FSD-204 without logging anyone out.
TSD-511Matrix save is per cell.One transaction: update cell, bump version, write audit, queue N-21 to affected users. A page of edits is many small saves, which is why the UI cycles a cell on click instead of a big form.

5.3 Enforcement points

5.4 Multi-role and segregation (Q-F6)

IDBehaviourDetail
TSD-520Permissions are the union of held roles.Nothing else changes for menus and policies; a person with two roles sees the union and acts under the union.
TSD-521One person, one step per chain.The resolver refuses to assign the same user to two steps of one document. Six phases, each ending in something a user can click and sign off. Order is dictated by dependency, not by convenience: nothing in the workflow can be built before the engine, and the engine is meaningless before there is something to approve.
